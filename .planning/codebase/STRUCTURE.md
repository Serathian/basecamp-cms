## Directory Purposes

**`src/app/(frontend)/`:**
- Purpose: Public-facing Next.js pages served to website visitors
- Contains: Layout, page components, CSS
- Key files: `src/app/(frontend)/page.tsx`

**`src/app/(payload)/`:**
- Purpose: Payload CMS admin panel and API endpoints — almost entirely auto-generated by Payload
- Contains: Admin UI pages, REST catch-all route, GraphQL route
- Key files: `src/app/(payload)/api/[...slug]/route.ts` (REST), `src/app/(payload)/admin/[[...segments]]/page.tsx` (admin UI)
- Note: Do not hand-edit generated files — they will be overwritten by `payload generate:importmap`

**`src/collections/`:**
- Purpose: The data model of the CMS — every content type, its fields, access rules, hooks, and custom endpoints live here
- Contains: One `CollectionConfig` export per `.ts` file, grouped by site namespace
- Key files: `src/payload.config.ts` (registers all of them)

**`src/collections/users/access/`:**
- Purpose: Reusable role-based access control functions shared by all collections
- Contains: `checkrole.ts` (base), `admin.ts`, `editor.ts`, `user.ts`, `anyone.ts`

**`src/collections/users/hooks/`:**
- Purpose: Payload field/collection hook implementations for the Users collection
- Contains: `protectRoles.ts` — prevents role self-escalation by non-admins

**`src/lib/`:**
- Purpose: Utility functions that are not collection-specific
- Contains: `nearby.ts` — raw PostGIS spatial query for proximity searches

**`src/migrations/`:**
- Purpose: Versioned database migration files; never auto-applied — always run explicitly
- Contains: Timestamped `.ts` files with `up`/`down` functions; `index.ts` barrel registers them with Payload
- Note: Never edit existing migration files; always create a new one

**`packages/types/`:**
- Purpose: Ships the auto-generated Payload types as a standalone npm package so consuming frontends get full type safety without installing Payload itself
- Contains: `index.ts` (re-exports), `package.json` (publish config), `tsconfig.json`
- Build: Copies `src/payload-types-export.ts` (generated by running `payload generate:types` with `payload.config.export-types.ts`), compiles to `dist/`, then removes the copy

**`tests/e2e/`:**
- Purpose: Playwright browser tests against a running dev server
- Contains: Admin panel navigation specs, frontend specs

**`tests/int/`:**
- Purpose: Vitest integration tests that hit the API
- Contains: `api.int.spec.ts`

**`tests/helpers/`:**
- Purpose: Shared test setup utilities
- Contains: `login.ts` (Playwright login helper), `seedUser.ts` (create/destroy test user)

## Key File Locations

**Entry Points:**
- `src/payload.config.ts`: Payload configuration — the single source of truth for the data model
- `src/app/(payload)/api/[...slug]/route.ts`: REST API entry point
- `src/app/(payload)/api/graphql/route.ts`: GraphQL API entry point
- `src/app/(frontend)/page.tsx`: Frontend home page

**Configuration:**
- `next.config.mjs`: Next.js build configuration
- `tsconfig.json`: TypeScript compiler options; defines `@/*` → `./src/*` and `@payload-config` → `src/payload.config.ts` aliases
- `.env.example`: Documents required environment variables (`DATABASE_URL`, `PAYLOAD_SECRET`)
- `docker-compose.yml`: Local Postgres service + app container

**Core Data Model:**
- `src/collections/jake-reddy/JrPosts.ts`: Blog posts for jake-reddy.com
- `src/collections/jake-reddy/JrProjects.ts`: Portfolio projects for jake-reddy.com
- `src/collections/nerdintheforest/NitfPosts.ts`: Adventure/outdoors posts (with geo + PostGIS)
- `src/collections/nerdintheforest/NitfTrails.ts`: Hiking trails with GPX auto-processing hook
- `src/collections/nerdintheforest/NitfWaypoints.ts`: Trail waypoints
- `src/collections/nerdintheforest/NitfLocations.ts`: Camp/shelter/viewpoint map markers
- `src/collections/reddyontheroad/RotrPosts.ts`: Travel posts
- `src/collections/reddyontheroad/RotrLocations.ts`: Travel location markers
- `src/collections/shared/Authors.ts`: Authors shared across all sites
- `src/collections/shared/Tags.ts`: Tags scoped per site
- `src/collections/Media.ts`: File/image uploads (shared)
- `src/collections/users/Users.ts`: CMS users with role-based auth

**Access Control:**
- `src/collections/users/access/checkrole.ts`: Base role check utility
- `src/collections/users/access/editor.ts`: Admin/editor gate (used by most write operations)
- `src/collections/users/access/anyone.ts`: Public read gate

**Utilities:**
- `src/lib/nearby.ts`: PostGIS `ST_DWithin` proximity query

**Generated (do not edit):**
- `src/payload-types.ts`: TypeScript types for all collections
- `src/payload-generated-schema.ts`: DB schema snapshot
- `src/app/(payload)/admin/importMap.js`: Payload component registry
- `src/app/(payload)/admin/[[...segments]]/page.tsx`: Admin page
- `src/app/(payload)/api/[...slug]/route.ts`: REST route handler
- `src/app/(payload)/api/graphql/route.ts`: GraphQL route handler
- `src/app/(payload)/layout.tsx`: Admin layout

## Naming Conventions

**Files:**
- Collection files: PascalCase matching the export name — `NitfPosts.ts` exports `NitfPosts`
- Access helpers: lowercase — `editor.ts`, `admin.ts`, `checkrole.ts`
- Hook files: camelCase — `protectRoles.ts`
- Lib files: lowercase — `nearby.ts`
- Next.js route files: `route.ts` (API) or `page.tsx` (UI), per Next.js convention

**Collection slugs:**
- Snake_case with site prefix: `jr_posts`, `jr_projects`, `nitf_posts`, `nitf_trails`, `nitf_waypoints`, `nitf_locations`, `rotr_posts`, `rotr_locations`
- Shared/system slugs: no prefix — `users`, `media`, `authors`, `tags`

**Directories:**
- Site namespaces under `src/collections/` use lowercase kebab: `jake-reddy/`, `nerdintheforest/`, `reddyontheroad/`
- Shared collections: `src/collections/shared/`

**TypeScript exports:**
- Collection configs: named export matching PascalCase file name — `export const NitfPosts: CollectionConfig`
- Access functions: default export for single-responsibility files (`editor`, `admin`, `user`), named export for utilities (`checkRole`, `anyone`)

## Where to Add New Code

**New collection for an existing site:**
- Implementation: `src/collections/{site-namespace}/{PrefixCollectionName}.ts`
  - e.g., a new nerdintheforest collection → `src/collections/nerdintheforest/NitfGear.ts`
- Register: Add to the `collections` array in `src/payload.config.ts` and `src/payload.config.export-types.ts`
- Create migration: `npx payload migrate:create` then implement `up`/`down` in the new file; register in `src/migrations/index.ts`

**New collection for a new site:**
- Create directory: `src/collections/{new-site}/`
- Slug prefix: choose a short prefix (e.g., `abc_`) and apply consistently
- Register: Same as above in `payload.config.ts`
- Add site option: Update the `sites` select field in `src/collections/shared/Authors.ts` and the `site` select in `src/collections/shared/Tags.ts`

**New access control rule:**
- Add to: `src/collections/users/access/` as a new `.ts` file
- Pattern: default-export a function `({ req: { user } }: any) => boolean | WhereClause`

**New utility function:**
- Add to: `src/lib/{name}.ts`
- Keep free of collection-specific knowledge where possible

**New custom Next.js API route:**
- Add to: `src/app/{route-name}/route.ts`
- Use `getPayload({ config: configPromise })` to access the Payload instance

**New migration:**
- Run: `npx payload migrate:create` to generate a timestamped file in `src/migrations/`
- Register: Add to the `migrations` array in `src/migrations/index.ts`
- Rule: Never edit existing migration files; always create a new one

## Special Directories

**`.next/`:**
- Purpose: Next.js build output and dev server cache
- Generated: Yes
- Committed: No

**`packages/types/dist/`:**
- Purpose: Compiled output of the types package
- Generated: Yes (via `npm run build` in `packages/types/`)
- Committed: No (in `packages/types/.gitignore`)

**`src/migrations/`:**
- Purpose: Versioned DB migrations
- Generated: Partially (scaffolded by `payload migrate:create`, then hand-edited)
- Committed: Yes — all migration files must be committed

**`src/payload-types.ts` and `src/payload-generated-schema.ts`:**
- Purpose: Auto-generated type and schema files
- Generated: Yes (by `payload generate:types`)
- Committed: Yes — consumed by application code and the types package build
